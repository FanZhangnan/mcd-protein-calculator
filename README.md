# 麦麦健身餐管家

麦当劳营养点餐助手（本地首版）。两个模式：

- **单餐（默认）**：每次吃之前，给出这一顿的蛋白质、脂肪、碳水和价格要求，推荐**一个汉堡 + 可选饮品**。严格模式：营养只取官方标准版，去除配料只写进点单参数，不扣减数值。
- **全天**：按热量/蛋白/脂肪/碳水目标与预算排出早、午、晚三餐；吃完一餐后记录实际摄入，只重排剩余餐次。

当前正式目标门店：**麦当劳珠海屏湾一路餐厅（`1440054`，到店自取 / 堂食）**。
上海 `1450713` 的实现与验证报告保留为历史版本（`02`、`03`）。

数据全部来自麦当劳中国 MCP 接口（菜单、营养、价格），不编造餐品或价格。**不存在「加肉饼」能力**，菜单的肉量差异只通过官方整款汉堡升级表达。

## 单餐模式（默认）

**每次吃之前，只算这一顿。** 输入：餐次、蛋白质下限、脂肪上限、价格上限（必填）；碳水/热量/允许配菜在「更多选项」里。

| 规则 | 说明 |
|---|---|
| 结构锁定 | **恰好 1 个主食，数量固定 1**；不会用 2 个汉堡补蛋白 |
| 饮品 | 0–1 杯，只从 零度可乐 / 美式 / 纯牛奶 + 官方热量 <20 kcal 的饮品中选；默认不加 |
| 配菜 | `allow_side=false` 时为 0，true 时最多 1 份 |
| 硬约束 | 价格、脂肪任何情况下不突破 |
| 排序 | 可行集 → 蛋白缺口最小 → 价格最低 → 脂肪最低 |
| 候选 | 全部枚举，不做 beam |
| 达标 | **只用官方标准版数值** |

### 严格模式

1. 营养只取官方营养表的整款单份数据。
2. 去酱/去芝士/去培根等只写进 `modification`，让用户点到该版本；**营养不扣减**。
3. 达标判断用标准版数值，去除建议不参与。
4. 文案固定：「建议去掉 X。去掉后的营养官方未提供，此处显示标准版数值。」
5. 去除项名称含 芝士/吉士/干酪/培根/蛋 时，追加「去掉 X 后，蛋白质可能低于显示值。」
6. 不新增组件估算，单餐不使用去酱估算情景。

### 点单建议

结果卡的「点单建议」列出该 SKU 实际支持去除的配料（酱、芝士、吉士、干酪、培根、黄油），默认不勾选。勾选后走 `suggest_remove`，整组特调参数一起传；取消即恢复标准版，幂等。

### 肉量升级阶梯

`data/upgrade_ladder.json` 人工维护同系列升级（如 麦香鱼 → 双层深海鳕鱼堡）。显示 `+蛋白 / +脂肪 / +元`，以及每多补 10 g 蛋白质多花多少钱、多多少脂肪。任一款不在售或无营养，该档隐藏。

### 无解时

不只显示红字，给出：

- 在脂肪 ≤ F、价格 ≤ B 下，这一餐蛋白质最多能达到多少（商品名）
- 只放宽脂肪 / 只放宽价格，各自需要多少
- 都达不到 → 「这家店当前菜单达不到 P g 蛋白质（整份最高 X g）」

### 快速估算（可选）

Mifflin-St Jeor 算 BMR → 乘活动系数得 TDEE → 减脂取 TDEE − 500 → 按每天餐数平均；蛋白质按 1.6 g/kg 分配。女性全天 <1200 kcal、男性 <1500 kcal 时提示。只是预填，可改。

## 界面怎么用

1. **目标与门店**：热量区间、蛋白下限、脂肪/碳水上下限、日预算、日期、三餐时间、去酱估算情景 → 保存目标。
2. **刷新真实菜单**：按「门店 + 日期 + 三餐时段」拉菜单，写入 `data/cache/{日期}__{门店}__{key}.json`。
3. **重新生成方案**：重新求解三餐，会清空当前数量与定制。
4. **为当前方案报价**：只对屏幕上的商品/数量/定制逐餐试算（`calculate-price`），**不会重新选餐**，也不会丢弃你的修改；签名不匹配或上下文已变会被拒绝。
5. **改数量**：待买只能填 1、2、3…（整数）；填小数 / 0 / 负数 / 空值会被拒绝并恢复原值，方案与签名不变。营养、行计与报价都按同一个整数计算。
6. **去酱（估算）**：只对**实际提供酱料特调项**的主食可勾选；取消即完整恢复标准版。
7. **记录为已吃**：填实际吃了多少（**可以填 0.5**）和记账金额（可留空）；记录锁定后只重排剩余餐次，**不会重新报价**。
8. **改记录**：可改每项已吃数量（可小数）、可单独改记账金额；改完自动重算剩余目标。

## 核心规则

### 1. 重排只有一套数学口径

> **只用「剩余目标」求解未吃餐次；已吃餐次只在最终评估时合并回全天。**

- 求解器（`plan_open`）永远收不到已吃数据；`open_meals=[]` 表示"没有开放餐次"，**不会**被当成三餐
- 减法只在 `Service.targets_after()` 发生一次，脂肪/碳水的**上下限一起减**
- 最终判定统一走 `planner.evaluate_day()`：全天合计（已吃 + 未吃）对比全天目标。数学上与"未吃合计 vs 剩余目标"等价，但只有这一套措辞，且三餐全吃时仍然成立
- 规划、重算、重排、当前方案报价四条路径都调用同一个 `compose_payload()`

### 2. 数量与金额语义

**两个数量不是同一个东西，不能互相转换：**

|  | 待买数量 | 已吃数量 |
|---|---|---|
| 允许值 | **正整数 1、2、3…** | **正数，可小数**（如 0.5 个汉堡） |
| 用途 | 营养合计、行计、`calculate-price` 请求 | 只用于摄入营养与剩余目标 |
| 非法输入 | 0.5 / 0 / 负数 / 空 / 非数字 / NaN / Inf → **400 `invalid_quantity`** | 0 / 负数 / 空 / 非数字 / NaN / Inf → **400** |
| 处理方式 | 不取整、不截断、不默认 1 | 不取整 |
| 报价 | 逐项发送整数，与界面完全一致 | **从不重新报价** |

- 前端 `min=1 step=1` 只是提示；后端 `purchase_quantity()` 独立校验，`quote_meal()` 也会拒绝小数，并且**在调用 MCP 之前**就拒绝
- 无效修改不改变最后一次有效工作快照 / 基线 / 签名，也不发起 `calculate-price`；界面恢复有效数量并说明原因
- 已吃 `0.5` 份：营养按半份计，**记账金额不会被除以 2**（买了整份 = 花了整份的钱）；金额来源仍是 `manual` / `quoted` / `unknown`

| 概念 | 字段 | 含义 |
|---|---|---|
| 每份营养 | `item.nutrition` | 官方**单份**标示值 |
| 数量 | `item.quantity` | 待买为整数；已吃可为小数 |
| 单价 | `item.price_ref` | 菜单参考价（单份） |
| 行计 | `item.line_total_ref` | 单价 × 数量 |
| 已吃记账金额 | `meal.amount_actual` | 记录时填写的真实金额，**只属于已吃餐次** |
| 记账来源 | `amount_source` | `quoted`（采用当时的试算价）/ `manual`（手填）/ `unknown` |
| 试算价 | `meal.quote` + `quotes` | `calculate-price` 的返回，**不是实付**，也不会写进 `amount_actual` |

全天金额分三个数，绝不混用：

| 字段 | 含义 | 何时为 `null` |
|---|---|---|
| `booked_total` | Σ 已吃记账金额 | 任一已吃记录缺金额 |
| `quote_total` | Σ 开放餐次成功试算 | 任一开放餐次试算失败 |
| `cost` | 全天合计 = booked + quote（或 booked + 参考价） | 上述任一未知 |

`budget_status` 取值：`quoted`（按试算价）/ `booked`（三餐全吃，按记账）/ `reference`（按参考价）/ `not_evaluated`（缺金额或试算失败）/ `no_budget`（未设预算）。

- 任一记录金额为空 → 全天预算 `not_evaluated`，**绝不按 0 处理**，也**不阻断营养重排**
- 试算失败同理：`cost=null`，不会被当成 0 元的一天

### 3. 营养匹配不做模糊合并

官方营养表是**标准版单份标示值**，不是门店实际份量测量值。绑定只认两种证据：

| 证据 | 状态标签 |
|---|---|
| 套餐 `rounds` 中 POS 自己标注的 code→名称 | 官方·别名 |
| 名称完全相同（仅统一括号宽度） | 官方 |

「玉米杯」不会自动当成「小杯玉米杯」；这类 SKU 进入"数据缺失"，不参与规划，也不按 0 处理。同名多条且数值不同 → 判冲突。

### 4. 去酱 = 能力校验 + 基线推导

- 基线存在 `baseline.json`，**不可变**；同时写入 `context`（门店/日期/时段/用餐方式）与 `plan_version`
- 换门店、日期、时段或用餐方式后，旧基线**加载时即被拒绝**（`409 stale_baseline`）；清内存不等于作废，磁盘上的基线同样不会复活
- 历史摄入记录不随方案失效删除
- 每次改数量/定制都从基线重建（`POST /api/recompute`），因此**幂等**：取消完整恢复、重复应用不累计
- 能力逐 SKU 查 `query-meal-detail`（带 `reservationDate`），只认带 `unselectedKey` 的酱料项
- 估算情景只适用于「麦香鸡酱」，其它酱料一律拒绝估算
- 生效时写入 `modification: [{code, key: unselectedKey, quantity:1}]`，报价与保存都带它
- 已锁定餐次不可再定制，也不可通过重算改数量（会提示去「已吃记录」里改）

### 5. 估算 = 并列情景，不是区间

| 情景 | 来源 | 替代配料 | 份量假设 | 钠 |
|---|---|---|---|---|
| 情景A | 二手整理（自称台湾官网，未核实原页） | 台湾「麥香鷄醬」 | 每份（未标克重） | 无 |
| 情景B | 中国妇幼保健协会引市售标签 | 普通蛋黄酱 | 15 g（未获门店确认） | 有 |

两个情景各自独立，**不拼成上下界**。去酱后的钠/钙按情景不同可能为未知；未知就显示未知。

### 6. 目标函数先归一化，先可行后偏好

```
score = 1.0 × |热量 − 区间中点| / 中点
      + 1.0 × max(0, 蛋白目标 − 实际) / 蛋白目标
      + 0.5 × 脂肪越界量 / 脂肪参考值
      + 0.5 × 碳水越界量 / 碳水参考值
      + 0.8 × max(0, 花费 − 预算) / 预算
      + 0.08 × 主食重复次数
```

顺序是：**先筛出满足硬约束的候选，再在其中取最小 score**。关键营养未知的候选直接判不可行。没有可行解时才给最接近方案，并注明「不视为达标，也不代表全局无解」。

### 7. 报价会回写预算

- 全部开放餐次报价成功 → `cost = booked_total + Σ 试算`，用该值重算预算差额与 `feasible`
- 任一报价失败/缺金额，或已吃记账金额缺失 → `budget_status = not_evaluated`，`cost = null`
- 试算价与已吃记账金额**语义分离**：报价永远不写进 `amount_actual`，也不会覆盖已吃金额
- 报价签名绑定 门店/日期/时段/用餐方式/商品/数量/定制/锁定状态；改数量、定制或重排后**旧签名立刻失效**
- `/api/quote` 只读当前方案快照，不调用求解器；签名不符返回 `409 stale_signature`，上下文变化返回 `409 stale_context`

### 8. 缓存按上下文隔离

`CacheContext = 门店 + 日期 + beType + orderType + 三餐时间`，哈希后进文件名；命中前逐字段比对。换门店或换时段会自动重新拉取，不会返回旧数据。数据来源分 `live` / `cache` / `offline` 三态并显示在界面顶部。

## 已知限制

- **午餐与晚餐菜单集合相同**，只能靠时点区分，做不了"晚餐专属"推荐。
- **部分热门 SKU 无营养映射**（新系列、未标规格的可乐/玉米杯/派），被排除在方案外。
- **加肉饼、少酱档位**在接口层不存在。
