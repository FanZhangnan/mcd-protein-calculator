# 麦当劳增肌计算器

**每一块钱，买到最多的蛋白质。**

给定「想吃够多少蛋白质」和「最多花多少钱」，在珠海屏湾一路餐厅（`1440054`）当前在售菜单里，枚举这一餐所有结构合法的组合，给出**最便宜的达标方案**；如果达不到，就告诉你**预算内最多能吃到多少克蛋白质**，以及只放宽某一项需要放宽到多少。

严格模式：所有营养数字都取麦当劳官方标准版整款数据。去掉配料只写进点单参数，**不扣减任何营养数值**。

## 输入

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `meal` | 是 | `breakfast` / `lunch` / `dinner` |
| `protein_min` | 是 | 蛋白质下限（g），达标目标 |
| `budget` | 是 | 价格上限（元），硬约束 |
| `fat_max` | 否 | 脂肪上限（g），填了就是硬约束 |
| `kcal_max` / `kcal_min` | 否 | 热量上限/下限（kcal），填了就是硬约束 |
| `allow_side` | 否 | 是否允许 1 份配菜，默认不允许 |
| `max_mains` | 否 | 主食数量上限，默认 2，可选 1 / 2 / 3 |
| `protein_tolerance` | 否 | 可接受比目标少几克蛋白质，默认 3，只接受 0–10 的整数 |

### 按身体数据估算（界面）

- 蛋白质：增肌 `2.0 g/kg`，维持 `1.6 g/kg`，除以每天餐数后预填到「蛋白质下限」。
- 热量：Mifflin-St Jeor 算 BMR，乘活动系数得 TDEE；增肌 `TDEE + 300`，按餐数平均。**只作参考显示，不预填为约束。**
- 预填后显示：「这家店这一餐，在价格 ≤ B 元时最多能买到 X g 蛋白质」，数据来自性价比图的前沿。

例：男，22 岁，175 cm，70 kg，每天 3 餐，增肌 → 蛋白质 `2.0 × 70 ÷ 3 = 46.7`，预填 47 g。

## 求解规则

1. 主食 1–N 个（N = `max_mains`）。可以是同一款 2 个，也可以是两款不同的；同一款 2 个会合并成一行、数量 2。
2. 饮品 0–1 杯，默认不加。白名单：纯牛奶、零度可乐、美式咖啡，以及官方热量 < 20 kcal 的饮品。
3. 配菜默认 0 份；勾选「允许配菜」后最多 1 份。
4. 硬约束：价格上限必须满足；用户填了脂肪或热量上下限时，也一并作为硬约束。**无解时的主卡片同样不许突破这些上限。**
5. 排序：先筛「蛋白质 ≥ 下限且全部硬约束满足」，再按 **价格最低 → 蛋白质最高 → 脂肪最低**。
5.1 容差：先按原目标求解；无解时才用「目标 − 容差」再求一次。原目标有解时，另给一个更便宜的容差组合作为「省钱选项」（`saver`）。
5.2 状态只有三种：`met` 达标、`near` 接近达标（显示真实蛋白质与缺口）、`under` 预算内最多。容差不会放宽价格、脂肪或热量。
6. 每个结果显示 **每元蛋白质 = 蛋白质 g ÷ 价格 元**，保留一位小数。
7. 候选全部枚举，不做 beam 截断。
8. 达标判断只用官方标准版数值。

#### 接近达标与省钱选项

- `near`：比目标少 X g，在允许的容差内；主卡片显示的是**真实蛋白质**，不会写成目标值。
- `saver`：只在主方案达标时出现，是价格更低、蛋白质仍 ≥「目标 − 容差」的组合；附带 `protein_less` 与 `money_saved`。
- 用户选择省钱方案时，用同一请求加 `"select":"saver"` 重新求解，报价随之切换。

## 无解时怎么显示

1. 第一行固定为：**当前条件下没有满足全部要求的方案**。
2. 主卡片 = 在全部硬约束下蛋白质最高的组合，标签「预算内最多」，并显示蛋白质缺口。
3. 没有任何组合满足硬约束时，**不显示商品卡片**。
4. 放宽方案只作为文字，逐条列出：
   - 只放宽价格：达到蛋白质目标需要的最低价格和对应组合；
   - 设了脂肪/热量上限时：只放宽这一项，需要放宽到多少。
5. 点单建议只针对主卡片上的商品。

## 点单建议与升级阶梯

- `suggest_remove`：从 POS 真实返回的可去项里生成，默认折叠，需用户勾选才生效。
- 勾选后只写 `modification` 点单参数，营养仍显示官方标准版；文案固定：
  - 「建议去掉 X。去掉后的营养官方未提供，此处显示标准版数值。」
  - 若该配料可能含蛋白质，追加「去掉 X 后，蛋白质可能低于显示值。」
- 名称含「芝士、吉士、干酪、培根、蛋」的去除项注明「增肌时不建议去掉，会减少蛋白质」。
- `protein_risk`：名称含「酱」的一律为 `false`（酱贡献脂肪，不贡献蛋白质）；「高达干酪片」为 `true`。
- 升级阶梯只保留肉饼（鸡排/鱼排）数量真正增加的配对：

| 从 | 到 | 增量 |
| --- | --- | --- |
| 麦香鱼 | 双层深海鳕鱼堡 | +12 g 蛋白质 / +3 元 |
| 猪柳蛋麦满分 | 双层猪柳蛋麦满分 | +6 g / +3 元 |
| 原味板烧鸡腿麦满分 | 双层原味板烧鸡腿麦满分 | +8 g / +4 元 |

显示「+蛋白质 / +价格 / 每多 1 元多多少 g 蛋白质」；蛋白质增量 < 5 g 时只显示实际差值，不做换算。每条都带 `evidence` 说明肉饼数量和官方蛋白质数值。
升级步骤还会代入当前全部硬约束：装不下时标灰并写明「升级后价格超出预算 X 元 / 脂肪超出上限 X g」，装得下则显示「升级后仍在限制内」。

## 蛋白质性价比图

- 接口：`GET /api/meal/landscape?meal=lunch&max_mains=2`
- 返回该餐次可售池中**所有能匹配官方营养的主食**：`code`、`name`、`protein`、`fat`、`kcal`、`price`、`protein_per_yuan`。
- 页面散点图：横轴价格、纵轴蛋白质；每元蛋白质最高的前 3 款高亮并标名称（标签自动避让）；悬停或手机点击显示名称、价格、蛋白质、脂肪、热量、每元蛋白质。
- 推荐方案按组合总价与总蛋白质画成星形标记，两个汉堡的组合也会画出来；有省钱选项时另用虚线圆点标出。
- 纵横轴上限 = 最大值 × 1.15，取整到 5 的倍数，保证达标区域不会被压扁。
- 填写目标后，图上画出达标区域（蛋白质 ≥ P 且价格 ≤ B）。
- 排行表按每元蛋白质从高到低列出，默认前 5、可展开到前 10；推荐方案里的商品会高亮。手机端改为卡片列表。
- 只用官方标准版数据，图下注明「严格模式：官方标准版数据」。图表为原生 SVG，不依赖外部图表库。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 页面 |
| GET | `/api/bootstrap` | 门店/日期/时段、缓存来源、营养目录、缺失清单、基线状态 |
| GET | `/api/meal/landscape` | 性价比图数据 + 预算→蛋白质前沿 |
| GET | `/api/removable` | 单 SKU 可去项（含整组 `selectedKey` / `unselectedKey`） |
| GET | `/api/ladder` | 肉量升级阶梯 |
| POST | `/api/refresh` | 按当前门店/日期/时段拉真实菜单 |
| POST | `/api/meal` | 求解这一餐 |
| POST | `/api/quote` | 为当前方案试算（不重新选餐） |
| POST | `/api/recompute` | 基线 + 数量/去料重算 |
| POST | `/api/settings` | 保存门店、日期、各餐次时间 |

`POST /api/quote` 必须带当前方案的 `signature`：

- `409 stale_signature`：签名与当前方案不一致；
- `409 stale_context`：门店/日期/时段已变化；
- `400 missing_signature`：没带签名。

`POST /api/recompute` 只接受 `suggest_remove`；其他动作返回 `400 unsupported_customization`，`supported` 为 `["suggest_remove"]`。

## 数据与缓存

- 来源三态：`live`（实时 MCP）/ `cache`（本地缓存）/ `offline`（fixture），界面顶部明确标注，绝不用离线数据冒充实时。
- 缓存按 `门店 + 日期 + beType + orderType + 各餐次时间` 哈希隔离；换门店或换时段会重新拉取。
- 特调查询按**餐次时间**缓存：同一 SKU 可能早餐在售、午餐下架（如 514700），午餐查询不会复用早餐结果。
- 营养匹配只认两种证据：`code → 名称` 别名（来自套餐 rounds），或括号宽度归一后的精确同名；同名不同规格不合并。

## 已知限制

- 早餐「纯牛奶(盒装)」在营养表中存在同名重复行，无法唯一匹配，因此不进入计算；不会按 0 处理。
- 可去项取决于 POS 是否返回 `unselectedKey`；没有返回的 SKU 不显示点单建议。
- 升级阶梯为人工维护的 3 对，新增配对需人工核对肉饼数量与官方营养。
- 报价是所选时段的试算参考价，不是结算价；以门店实际收款为准。
- 价格上限、脂肪上限用菜单参考价判定；试算价若高于参考价，结果卡会按试算价重新判定并标注。
- 单次只计算一餐，不记录历史、不做跨餐累计。
