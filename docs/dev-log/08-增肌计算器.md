## 二、求解规则落地

1. 主食 1–N 个（N 默认 2，可设 1）；同一款 2 个合并为一行、`quantity=2`，报价只发一条 POS 行。
2. 饮品 0–1 杯，白名单：纯牛奶、零度可乐、美式咖啡，或官方热量 < 20 kcal。
3. 配菜默认 0，勾选后最多 1。
4. 硬约束：`budget` 必填；`fat_max`、`kcal_min/max` 填了才生效。无解主卡片同样受约束。
5. 排序键：`(价格, -蛋白质, 脂肪)`；无解回退键：`(-蛋白质, 价格, 脂肪)`。
6. `protein_per_yuan = round(protein / price, 1)`。
7. `build_meal_options()` 全量枚举，无 beam。
8. `is_feasible()` 只看官方数值。

代码位置：`src/planner.py`（`build_meal_options` / `plan_open` / `single_meal_frontier`）、`src/service.py`（`plan_meal` / `landscape` / `upgrade_for`）。

## 三、无解修复（原 bug）

原问题：午餐 P≥40 / F≤20 / ¥≤35 时，主卡片是脂肪 44 g 的培根安格斯厚牛堡 —— 它违反了脂肪上限，却被当作「最接近方案」展示。

修复后的判定链：

```
候选 → caps_ok(价格/脂肪/热量) → 有可行解？
  ├─ 是：min(价格, -蛋白质, 脂肪)
  └─ 否：硬约束内 max(蛋白质, -价格, 脂肪) → 主卡片「预算内最多」
          └─ 硬约束内一个都没有 → items = []，不出卡片
```

验收用例 2（P≥40 / ¥≤25）实测：主卡片为双层深海鳕鱼堡 28 g / 21 g 脂肪 / 25 元，缺口 12 g；只放宽价格需 39 元（双层吉士 + 麦香鸡）。没有把 44 g 脂肪的商品放进卡片。

## 四、点单建议与升级阶梯

### 4.1 建议列表

- 来源：`GET /api/removable`（POS 真实 `modification`），按主食逐个取，覆盖主卡片上的每个主食。
- 默认折叠，用户勾选后才进入 `modification`；营养保持官方标准版。
- `protein_risk`：名称含「酱」→ 恒 `false`；「高达干酪片」「培根」→ `true`。
- 名称含「芝士、吉士、干酪、培根、蛋」的项附「增肌时不建议去掉，会减少蛋白质」。

## 九、边界

不发单、不取消订单、不领券、不兑换积分、不新增地址、不输出 Token。所有验收使用隔离目录 `MAI_MAI_DATA=/tmp/mai-live*`，用户真实 `data/` 未被写入。

## 十、已知限制

- 早餐「纯牛奶(盒装)」营养表存在同名重复行，无法唯一匹配，不进入计算。
- 可去项取决于 POS 是否返回 `unselectedKey`。
- 升级阶梯仍需人工维护（当前 3 对）。
- 报价为时段试算参考价，不是结算价。
- 价格/脂肪上限按菜单参考价判定；试算价更高时结果卡会按试算价重新判定并注明。
