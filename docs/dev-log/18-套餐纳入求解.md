# 18 · 套餐纳入求解（分支 `feat/combos` → `main`）

> 目标：把 `query-meal-detail` 返回 rounds 的套餐（三件套、随心配、超值早餐等）纳入求解，验证「套餐 + 单品」是否比纯单品组合更划算。
> 边界：只读 MCP（`query-meals`、`query-meal-detail`、`list-nutrition-foods`、`calculate-price`、`now-time-info`）；不领券、不下单、不输出 Token。
> 分支：先在 `feat/combos` 完成并跑通全部测试，再 fast-forward 合并到 `main`。

## 一、结论

| 场景 | 改前 | 改后 | 判断 |
| --- | --- | --- | --- |
| 午餐 44 g / 45 元 | 双层吉士汉堡 ×2，**54 g / 45.00** | 酥脆无双套餐（饮品换纯悦）+ 双层吉士汉堡，**50 g / 40.50** | 便宜 4.50 元，仍达标（多 6 g） |

## 二、套餐怎么识别

- **判定只看 `query-meal-detail` 的 `rounds`**，不看名字。构建脚本对每个餐次的**全部 SKU**（本次早餐 95、午餐 103）逐个查详情，`rounds ≥ 2` 判为套餐。
- 名字命中 `COMBO_WORDS` 只作为「没有套餐目录时」的兜底过滤；有目录时 `pools()` 以目录里的 `combo_code` 为准。名字带「套餐」但没有 rounds 的商品不会被误判。
- **会员价套餐排除**：`withOrder`、`discountType`（如「随单购早餐卡优惠」）、分类名或标签含「早餐卡 / 麦金卡 / 会员 / 专享」的整款跳过。本轮排除分类：`6折起早餐卡专区`。

## 三、只有一轮选项的商品（按单品处理）

新地、麦旋风、麦麦脆汁鸡1块这类商品，POS 只返回**一轮**（口味 / 规格选择）。它们不是套餐，而是一个可以单点的商品：

- 判定：`rounds == 1` → 单轮商品；构建脚本用**菜单名优先、轮内选项名兜底**去匹配官方营养，匹配不到就整款排除（不按 0 算）。
- 归池：按匹配到的名称分类——主食 / 小食 / 饮品 / **甜品**（新增分类）。甜品可单点，但不参与组合（不作为主食、不作为加购配菜），会出现在「门店与数据说明」里。
- 本轮实际纳入的单轮商品：

| --- | --- | --- | ---: | ---: |

| 可乐 `9900008751` | 可乐小杯 | 饮品 | 9.50 | 0 g |
| 新地 `9900008745` | 朱古力新地 | 甜品 | 12.00 | 5 g |

- **对三个场景的影响**：
  - 午餐 44 g / 45 元：**不变**（50 g / 40.50 元）。
  - 午餐 35 g / 25 元：主推荐**不变**（双层深海鳕鱼堡 28 g / 25.00 元）；但「加预算」提示从 34.50 元降到 **32.00 元**（酥脆无双套餐 + 汉堡包 = 36 g）——这是汉堡包进入主食池带来的。
  - 早餐 25 g / 20 元：主推荐**不变**（原味板烧鸡腿炒双蛋堡 27 g / 18.50 元）。单轮商品在早餐只贡献了甜品与可乐小杯，不参与组合。
  - 页面首屏默认（午餐 40 g / 45 元）从 42 g / 39.00 元变成 **40 g / 36.50 元**（双层吉士汉堡 + 汉堡包）——同一原因：麦香鸡涨到 16.5 元，汉堡包 14 元成了更省的补足。

## 四、变体与价格

每个套餐最多两个变体：

| 变体 | 规则 |
| --- | --- |
| `default` | 各轮取 POS 默认选项（`isDefault=1`） |
| `muscle` | 饮品轮换成白名单（纯牛奶 / 零度可乐 / 美式 / 官方热量 < 20 kcal），同蛋白时优先不加价；小食轮换成蛋白质更高的选项；**任何替换都不允许降低蛋白质**，否则保留默认 |

- **营养**：各轮所选单品的官方营养逐项相加；任一项匹配不到 → 整个变体标 `nutrition_unknown` 并排除。
- **参考价**：`菜单价 + Σ diffPrice`，并用带 `roundList` 的 `calculate-price` 真实试算逐一核对，**不一致就排除**。本轮 31 个变体全部一致；核对过程确实拦下了「精选单人餐三件套」（参考价 35.00 / 试算 37.50）和「板烧鸡腿堡三件套」（试算返回 60006 售罄）。
- 目录按「门店 + 日期 + 餐次时间」校验，过期或换店不加载。

## 四之二、这一轮踩到的三个坑

### 1. 目录的日期必须和服务当前用的日期一致

`Service.combo_catalog()` 会核对目录的 `context.date` 与当前缓存的日期；对不上就**整份拒用**，
`combos.catalog.available` 变成 `false`，页面提示「套餐目录未加载」，推荐悄悄退回纯单品。

而服务的规划日默认是**服务器日期 + 1 天**。所以：

- 目录要按「明天」构建，不是随便哪天；
- 测试不能自己往 `/api/settings` 写日期。`tests/ui_final.mjs` 原来会写死「明天」，
  服务一旦被切到别的日期，整份套餐目录就失效了 —— 表现是「推荐从 50 g / 40.50 变回 54 g / 45.00」，
  但代码没变。现在它只调 `/api/refresh`，保留服务自己的规划日。

### 2. 门店会拒绝对过去时点的查询

08:15 之后再查当天 08:15，接口返回 `600053 预约时间必须为未来时间`，菜单为空。
凌晨构建时这是"未来"，白天就变成"过去"了 —— 同一份代码，两次跑出不同结果。
`scripts/probe_menu_stability.py` 会持续打印 SKU 集合指纹，用来看菜单什么时候稳定；
`scripts/verify_combo_stability.py` 连跑两轮并只比较业务数量（SKU / 套餐 / 变体 / 排除数 + 变体指纹），
用来确认这一份目录是不是稳定的。

### 3. 券会轮换

门店的券是按活动发的，会换。本轮门店只剩「9.9元中杯冰美式」（适用麦咖啡™冰美式中杯），
之前那张「11.9元麦辣鸡腿堡」已经不在门店可用券里（卡包里还有，但在 POS 上带券试算已经不降价）。

`tests/coupon_ui.mjs` 原来断言固定的券名和固定的券后价，现在改成先问服务端当前有什么券，
再按实际情况断言：有可用券 → 断言券后价、券名、原价划线、券后每元、下单提示；
无可用券 → 断言「暂无可用券」、不显示券后价数字、价格区仍是参考价。
**没有删任何断言**，两条分支都还覆盖，DOM 里不出现 couponId / couponCode 始终校验。

## 九、已知限制与合并风险

1. **套餐目录是构建产物，不是实时查询**。一次构建要查 198 个详情 + 数十次试算，实时 MCP 约 6 分钟，不能放在页面请求里。目录按「门店 + 日期 + 餐次时间」校验；没有目录时页面明确提示，不会报错，也不会假装算过套餐。
2. **次日的菜单在凌晨仍会变动，而且过了取餐时点就查不到菜单**（`预约时间必须为未来时间`）。目录必须按未来的一天构建，并且和服务当前的规划日一致，否则整份目录会被拒用。目录与快照都是构建那一刻的快照，隔天必须重建。
3. **单轮商品的处理与任务书字面不同**：任务书写「有 rounds 的商品都识别为套餐」，实现要求至少两轮，否则新地、麦旋风、麦麦脆汁鸡1块会被当成套餐并绕过结构规则。这是有意的收紧，不是遗漏。
4. **会员价套餐全部排除**（52 个）。持早餐卡 / 麦金卡的用户实际最优会不同，但本工具没有账号上下文。
5. **31 个套餐因营养未知无法参与**（1+1 随心智、部分 500 大卡套餐等）。这不是「不如单品」，而是「无法按严格模式计算」。
6. **套餐与券后价互斥**：含套餐的方案直接返回 `unsupported`，即使另加的单品主食本可用券。这是按任务要求做的产品取舍。
7. **甜品不参与组合**：可以单点、在数据说明里可见，但不会被用来凑蛋白质或填预算。
8. **快照体积 0.60 MB**（含套餐后），一致性测试约 6 分钟。

## 十、上线修复：套餐核查那一行改读套餐目录

上线后发现：在线页结果卡底部写的是「已查 103 个 SKU，识别 **17** 个套餐，纳入 33 个变体；排除 **0** 个」，而构建产物是 50 个套餐、33 个变体、45 个排除（会员价 16 + 营养未知 29）。

原因在在线快照桩：`docs/demo/snapshot-shim.js` 的 `combosByMeal()` 拿快照里的 `comboVariants` 现算统计——`combos_found` 数的是「活下来的变体涉及几个套餐编码」（17 个），`excluded` 直接写死 0。本地页走 `/api/meal` 的 `combo_report()`，数字一直是对的；错的只有在线页。

修法：

- 统计只算一次：`combos.report_from_meal()`（`src/combos.py`）。`/api/meal` 与快照都调它，口径就是 `data/combo_catalog.json` 的 `checked / combo_count / variants / excluded / reasons`。
- 快照里每个餐次多一个 `comboReport`：`scripts/export_demo_snapshot.py` 导出时写入；只重建目录、不动菜单时，用 `scripts/attach_combo_report.py` 补写（先校验门店 / 日期 / 餐次，再校验快照变体数与目录一致，不一致就拒绝写）。
- 排除原因固定按「会员价、营养未知、价格不一致、试算失败」排列，页面写成「排除 45 个（会员价 16、营养未知 29）」。
- 断言：`tests/test_demo_combo_report.py` 逐餐次比对快照与目录；`tests/demo_ui.mjs` 比对页面那一行与 `combo_catalog.json`（同时比对页头徽标的组合数）；`tests/catalog_status_ui.mjs` 在本地服务上比对同一行。

修复后（2026-10-23 菜单）：午餐「已查 103 个 SKU，识别 50 个套餐，纳入 33 个变体；排除 45 个（会员价 16、营养未知 29）」，早餐「95 / 41 / 4；排除 38 个（会员价 36、营养未知 2）」。本地 `tests/test_*.py` 142 项、`demo_ui` 17 项、`catalog_status_ui` 7 项全部通过。
