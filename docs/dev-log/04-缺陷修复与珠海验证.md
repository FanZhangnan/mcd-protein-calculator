## 1 修复顺序

底层 → 接口 → 界面：

```
缓存上下文键  →  求解器选解  →  重排口径  →  数量/金额  →  去酱基线与能力  →  报价回写  →  门店迁移  →  文档/验收
```

先做前两项，是因为它们决定了后面所有「合计」是否可信；重排口径必须建立在"单个口径"上，否则数量与金额修好了也仍然算错。

## 2 逐项：根因 / 修改 / 回归

### 2.1 重排不能重复扣除已吃营养

**根因**
`server._replan` 先算出剩余目标，又把 `locked` 传给 `planner.plan()`；`planner` 把已吃餐次算进 `totals`，再拿这个「全天合计」去和「剩余目标」比较。两个基准混用，导致剩余下限根本没被检验（用户复现：剩余 935–1335，返回全天 1259 却仍判可行）。

**统一口径**（二选一，本文选后者并写死）
> **只用剩余目标求解开放餐次；已吃餐次只在展示层合并。**

- `planner.plan_open(pools, remaining_targets, open_meals)` —— 求解器**永远看不到已吃数据**
- `planner.merge_locked()` —— 只做展示合并，`feasible` 仍来自开放餐次的判定
- `Service.targets_after()` —— 唯一做减法的地方，脂肪/碳水的**上下限一起减**（旧版只减上限）

**修改文件**：`src/planner.py`（`plan_open` / `merge_locked` / `plan`）、`src/service.py`（`targets_after`、`plan`）、`src/server.py`（`_replan`）

**回归**：`R1`（565 已吃 → 开放餐次必须落在 935–1335，且全天 = 565 + 开放合计 ≥ 1500）、`R2`（fat_min/carb_min 一并递减）；HTTP 检查「重排只开放午晚」「可行性按剩余口径」。

### 2.2 数量与实际金额必须进入汇总

**根因**
`record_meal` 存了 `quantity`，但 `Item` 没有这个字段，`_sum_nutrition` 直接对单份营养求和；预算侧用 `price_ref`（参考单价）而不是记录下来的实际金额。

**语义（已写进代码注释与 README）**

| 概念 | 字段 | 含义 |
|---|---|---|
| 每份营养 | `item.nutrition` | 官方**单份**标示值 |
| 数量 | `item.quantity` | 份数 |
| 单价 | `item.price_ref` | 菜单参考价（单份） |
| 行计 | `item.line_total_ref` | `单价 × 数量` |
| 整餐实付 | `meal.amount_actual` | 记录时填写的实际金额，可空 |
| 金额来源 | `amount_source` | `quoted` / `manual` / `unknown` |

- `sum_nutrition()` 一律 `nutrition × quantity`
- 剩余预算 = 日预算 − Σ `amount_actual`
- **任一记录金额为空 → `budget_unknown=true`，剩余预算返回 `None`**，绝不按 0 处理
- 金额缺项**不阻断营养重排**，只把预算标为 `not_evaluated`（`R5` + HTTP 检查）

**修改文件**：`src/planner.py`（`Item.quantity`、`sum_nutrition`、`sum_reference_cost`）、`src/service.py`（`_normalise_items`、`record_meal`、`update_record`、`remaining_targets`）、`src/server.py`（`PATCH /api/intake/{id}`）、`web/app.js`（数量输入、记录编辑、改金额）

**回归**：`R3`（400 kcal × 2 = 800）、`R4`（实付 50 扣 50，不用参考价 10）、`R5`（金额空 → 不是 0）、`R6`（改数量+金额后重算）、`R7`（撤销恢复预算）。

### 2.3 去酱必须校验能力，并从标准版基线重算

**根因（三个叠在一起）**
1. 前端给所有 main 显示去酱，后端**不检查该 SKU 到底有没有酱料特调项**，也不检查估算情景是否适用；
2. `toggleCustom` 把**已经定制过的 PLAN** 当基线，空定制无法恢复；
3. 重复应用会在已扣减的营养上再扣一次 → 485 → 417 → 417 → 349。

**修复**

| 机制 | 实现 |
|---|---|
| 不可变基线 | `baseline.json`（`Service.set_baseline/get_baseline`），从不被覆盖式修改 |
| 每次从基线推导 | `POST /api/recompute` 接收 `quantities` + `customizations`，从基线重建，**幂等** |
| 能力校验 | `Service.sauce_capability(code)`：带 `reservationDate` 调 `query-meal-detail`，只认 `name` 含「酱」且带 `unselectedKey` 的选项 |
| 情景适用性 | `estimator.scenarios_for(component)`：两个情景只覆盖「麦香鸡酱」，其它酱一律拒绝估算 |
| 重新判定 | recompute 末尾用剩余目标重算 `feasible` / `violations` |
| 锁定保护 | `locked` 餐次的定制请求直接进 `issues`，不生效 |
| 定制参数 | 生效时写入 `item.modification = [{code, key: unselectedKey, quantity:1}]`，报价与保存都带它 |

**实地证据（珠海 `1440` 麦辣鸡腿汉堡，真实接口）**

```
official 1440: 485 kcal / protein 24
apply#1: kcal=417.0 sodium=None  est=True  issues=0
cancel : kcal=485.0 sodium=1208.0 est=False issues=0
apply#2: kcal=417.0 sodium=None  est=True  issues=0
```

用户描述的 485 → 417 → 417 → 349 **不再复现**，取消后完整回到 485（含钠 1208）。

**定制报价携带参数**：

```json
{"productCode":"1440","quantity":1,
 "modification":{"values":[{"code":"100136","key":"0-0","quantity":1}]}}
→ status=ok, amount=23.00, reservationDate=2026-10-20 12:15
```

**修改文件**：`src/service.py`（`sauce_capability` / `recompute` / `set_baseline` / `get_baseline`）、`src/estimator.py`（`scenarios_for`）、`src/server.py`（`/api/recompute`、`/api/capability`）、`web/app.js`（只对可用 SKU 显示去酱、取消即恢复）

**回归**：`R8`（应用→417，取消→369）、`R9`（三次应用同值，且 ≠ 第二次扣减值）、`R10`（无可去酱料的 `9900003586` 被拒）、`R11`（`烤味酱` 套用麦香鸡酱情景被拒）、`R12`（定制后 feasible 重算）。

### 2.4 最终报价后重验预算，并使旧报价失效

**根因**
`_plan` 只把 quotes 附加到返回体，没有更新 `cost`、预算差额和 `feasible`。参考合计 110 / 预算 110 时，真实报价 1500 仍会返回 `feasible=true`。

**修复**
`Service.apply_quotes()` 成为唯一回写口：

- 全部报价成功 → `cost = Σ 报价`，用该值重算 `violations` 与 `is_feasible`
- 任一报价失败或缺金额 → `budget_status="not_evaluated"`、`quote_total=None`、`feasible=false`（有预算时），并追加一条「预算尚未完成评估」
- 区分 `reference_total`（参考价合计）与 `quote_total`（成功试算合计）
- 报价签名 `plan_signature` 绑定 门店 / 日期 / 餐次时间 / 商品 code / 数量 / 定制；`recompute`、`replan`、改数量一律返回 `quotes_valid=false`，界面清空旧报价

**回归**：`R13`（报价 3×500=1500 > 预算 110 → feasible 翻为 false）、`R14`（有一笔失败 → 不计合计、标 `not_evaluated`）、`R15`（数量变化 → 签名变化）；HTTP 检查「报价合计已回写 97.5」。

### 2.5 缓存关联与珠海迁移

**根因**
缓存只按 `date` 命名，`ensure_cache` 也只比日期。改门店或改早餐时间后，内存缓存与磁盘文件仍命中旧上下文 → 配置 1440054/09:00，拿到的还是 1450713/08:15。

**修复**
`CacheContext(store_code, date, be_type, order_type, meal_times)` → `sha1[:12]` 作为键：

- 文件名 `{date}__{store}__{key}.json`
- 命中前逐字段比对上下文，不一致即重新拉取
- 内存缓存同时比对 `_cache_key`；换上下文自动失效
- `detail_cache`（特调能力）键也含门店/日期/餐次时间
- `/api/targets` 保存后调用 `invalidate()`

**回归**：`R16`（换店 + 换时段 → 缓存上下文同步变化）、`R17`（同一天两个上下文 → 两个缓存文件）、`R18`（`OfflineProvider` 的 `source` 必须是 `offline`，重载后为 `cache`，永不标 `live`）；HTTP 检查「缓存按门店/时段切换 + key 变化」。

### 2.6 求解器必须优先选择满足硬约束的候选

**根因**
最终只在 beam 结果里取 `score` 最小者，没有先筛可行集。合成反例中 B（2000 kcal / 99 g 蛋白，蛋白差 1 g）比 A（2200 kcal / 100 g）分低，于是选了 B 并报不可行。

**修复**
1. 先对每个候选算 `is_feasible()`（硬约束全满足、关键营养不能未知）
2. 有可行集 → 在可行集内取最小 `score`
3. 无可行集 → 取最接近，并注明「不视为达标，也不代表全局无解」
4. 关键营养为 `None` → 直接判不可行（`R20`）

**回归**：`R19`（A 胜出且 feasible=True，全天 2200 kcal / 100 g）、`R20`（蛋白未知 → 不可行 + `unknown` 违规项）。

### 2.7 产品验收补齐

| 项 | 处理 |
|---|---|
| 来源标注 | `provider.source_name`：`live` / `offline`；缓存重载后降级为 `cache`；界面顶部显示「实时 / 缓存 / 离线」 |
| 记录编辑 | 记录卡内可改每项数量（`PATCH /api/intake/{id}`），可单独改实付金额；改完自动重排 |

| 文档一致性 | 本文与 README 已按新实现改写；`02`/`03` 保留为上海历史版本，不覆盖 |

## 6 剩余限制

1. **午餐/晚餐菜单集合仍相同**，只能靠 `reservationDate` 时点区分。
2. **部分 SKU 无营养映射**（新系列、未标规格的可乐/玉米杯/派），被排除在规划外。
3. **加肉饼、少酱档位**在接口层不存在，首版不做。
4. **估算仍只覆盖整份「麦香鸡酱」**，且两个情景的份量依据不完整（A 无克重，B 的 15 g 未确认）；其它酱料无来源，一律拒绝估算。
5. **换配仍是独立接口**，未接入三餐求解，不参与全天合计。
6. 报价是**该时段试算参考价**，不承诺未来结算价；改数量/定制/重排后旧报价立即作废。
7. 菜单名分类依赖关键词表（`MAIN_WORDS`/`SIDE_WORDS`/`DRINK_WORDS`），存在误归类风险。
8. 单用户、单门店、到店自取；外送与账号体系未做。
