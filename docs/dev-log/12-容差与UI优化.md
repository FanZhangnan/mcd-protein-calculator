## 一、蛋白质容差

### 1. 服务端规则

`POST /api/meal` 新增可选参数 `protein_tolerance`：单位 g，默认 **3**，只接受 0–10 的整数（`3.5`、`"abc"`、`-1`、`11` 都是 400）。

求解顺序：

1. 先按原目标 `P` 求解，其他硬约束不变。
   - 有解 → 主方案 = 原规则下的最便宜达标组合，`protein_status = "met"`。
   - 同时求一次 `P − t`：若得到的组合更便宜，作为 `saver` 返回（`items`、`protein`、`cost`、`protein_less`、`money_saved`），只返回最省钱的一个。
2. `P` 无解 → 用 `P − t` 求解。
   - 有解 → 主方案 = 这个组合，`protein_status = "near"`，`protein_gap = P − 实际蛋白质`。
   - 仍无解 → 现有无解逻辑（预算内最多 + 放宽方案），`protein_status = "under"`；**放宽方案仍按原目标 `P` 计算**。
3. `protein_tolerance = 0` 时，`P − t = P`，两条分支与改动前完全一致。
4. 返回的蛋白质永远是接口真实值，从不把 42 g 写成 44 g。

前端「更多选项」新增「可接受少几克蛋白质」，默认 3；切换省钱选项时会用 `select: "saver"` 重新求解，所以报价针对的一定是当前展示的方案。

### 2. 新增/变化的返回字段

| 字段 | 含义 |

## 二、页面 UI

### 1. 页面顺序

| 位置 | 改动前 | 改动后 |
| --- | --- | --- |
| 页头 | 标题 + 副标题 + `cache` 时间、门店、营养条目数（长串 meta） | 标题 + 一句话说明 + 「非麦当劳官方产品」 |

### 2. 结果卡

- 顶部两个大数字：**蛋白质 X g**、**价格 Y 元**。价格只出现一次：有试算价时显示试算价并标「已试算」，否则显示参考价并标「参考价」。
- 状态标签：`达标` / `接近达标（少 X g）` / `预算内最多`。
- 第二行：每元蛋白质、热量、脂肪、碳水。
- 商品行：名称 × 数量 + 单价，每份营养放进可展开的「明细」。
- 无解/接近达标提示合并为一个框，最多三行：结论、预算内最多、放宽方案（多条放宽用「；」合并）。
- 点单建议、肉量升级默认折叠。
- 升级阶梯新增约束检查：服务端把升级后的组合代入当前价格/脂肪/热量上限，返回 `fits` 与 `fit_note`；超限的步骤整块标灰，并写「升级后价格超出预算 X 元、脂肪超出上限 X g」，满足时写「升级后仍在限制内」。

### 3. 蛋白质性价比图

- 推荐方案按**组合总价/总蛋白质**画成星形标记（两个汉堡的组合也会画）；有省钱选项时另画虚线圆点。
- 纵横轴上限 = `max(目标, 所有点, 推荐方案, 省钱选项) × 1.15`，向上取整到 5 的倍数；纵轴始终包含目标，达标区域不会被压成 0 高度。
- 前 3 名标签先按右上/左上/右下/左下放置，再按实际 `getBBox()` 做碰撞检测，必要时上/下移并加引导线；放不下时才隐藏。
- 悬停与手机点击都显示：名称、价格、蛋白质、脂肪、热量、每元蛋白质。
- 图例只保留四项：推荐方案、每元蛋白质前 3、其他主食、达标区域。

### 复跑方式（各脚本要求的运行模式不同）

每个脚本都要配一个**独立数据目录 + 独立端口**，不要复用用户原服务（8765）。

| 脚本 | 服务模式 | 启动命令 | 说明 |
| --- | --- | --- | --- |
| `test_*.py`（单元） | 无需服务 | `MAI_MAI_DATA=/tmp/x python3 -m tests.test_tolerance` | 直接跑 |
| `acceptance_http.py` | 离线 | `MAI_MAI_DATA=/tmp/x python3 src/server.py --offline --port 8791` | 隔离跑 |
| `acceptance_tolerance.py` | **实时** | `MAI_MAI_DATA=/tmp/x python3 src/server.py --port 8793` | 需要真实门店菜单 |
| `browser_muscle.mjs` | **离线** | `MAI_MAI_DATA=/tmp/x python3 src/server.py --offline --port 8797` | 「省钱选项」断言依赖离线 fixture 里存在更便宜的容差组合；实时菜单组合空间不同，可能没有 saver |
| `stories_shots.mjs` | **实时** | `MAI_MAI_DATA=/tmp/x python3 src/server.py --port 8798` | 截图取自真实门店菜单 |
| `ui_final.mjs` | 实时或离线均可 | 同上 | 桌面 + 手机 5 场景 |
| `boundary_ui.mjs` | **两个离线服务** | 见下 | 需要两个 URL |

`boundary_ui.mjs` 的两个服务：

```bash
# 第一个：把 lunch 设成 10:30，验证「落在两个供餐时段之间」
MAI_MAI_DATA=/tmp/mai-gap python3 src/server.py --offline --port 8800
curl -s -X POST http://127.0.0.1:8800/api/settings -H 'Content-Type: application/json' \
  -d '{"store":{"code":"1440054"},"date":"2026-10-21","meal_times":{"breakfast":"08:15","lunch":"10:30","dinner":"18:30"}}'

# 第二个：必须带 MAI_MAI_QUOTE_FAIL=1 才会模拟报价失败
MAI_MAI_DATA=/tmp/mai-fail MAI_MAI_QUOTE_FAIL=1 \
  python3 src/server.py --offline --port 8801

node tests/boundary_ui.mjs http://127.0.0.1:8800/ http://127.0.0.1:8801/
```

两个易踩的坑：

1. **浏览器脚本的 Chrome 调试端口会残留**。上一次运行被中断后，`/tmp/chrome-cdp-*` 与调试端口（`browser_muscle` 用 9335、`stories_shots` 用 9337、`boundary_ui` 用 9338、`ui_final` 用 9341）会被占住，下一次启动会连到旧实例上表现为「页面加载超时」。重跑前先清干净：

   ```bash
   lsof -ti :9335 | xargs kill -9; rm -rf /tmp/chrome-cdp-muscle
   ```

2. **实时验收会改写 `data/fixtures/` 里的证据文件**（时间戳、实时价格）。跑完如果差异只是时间戳，用 `git checkout -- data/fixtures/` 回滚，避免把噪音提交进去。
