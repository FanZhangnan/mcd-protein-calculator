## 一、三项必要验证

### 1. 套餐换配的最终报价

**指定的起点 `9900005456`（麦辣鸡腿堡三件套）已不可售，无法报价。**

| 调用 | 参数 | 返回 |
|---|---|---|
| `query-meal-detail` | code=9900005456（含 reservationDate=2026-10-19 18:30） | `success:false`, `code:60001`, `未匹配到商品，请重新拉取全量商品列表` |
| `query-meal-detail` | code=9900005456（不带 reservationDate） | 同上 |
| `calculate-price` | items=[9900005456×1] | `success:false`, `code:60006`, `商品已售罄或不可售，换一个商品或检查orderType/beType` |
| `query-meals` | 2026-10-19 12:15 / 18:30 | 菜单 SKU 集合中**不含** `1440` 与 `9900005456` |

原因：该门店当前菜单已切换到「龙焰」系列，麦辣鸡腿堡及其套餐不在售。这是门店/菜单事实，**不代表所有门店永久不支持**。

**改用同机制的可售套餐 `9900005462`（板烧鸡腿堡三件套）验证换配报价链路。**

真实组成（`query-meal-detail`，2026-10-19 00:32 抓取）：

| round | 名称 | 默认项 | 可换项（diffPrice） |
|---|---|---|---|
| 1 | 板烧鸡腿堡 | `1406` 板烧鸡腿堡 +¥0 | 仅 1 项 |
| 2 | 选择套餐内小食 | `4810` 中薯条 +¥0 | `521983` 心形薯饼 +¥1 / `521901` 扭扭薯 +¥1.5 / `4820` 大薯条 +¥2.5 |
| 3 | 选择套餐内饮料 | `3050` 可乐中杯 +¥0 | 共 26 项，+¥0 ～ +¥13 |

最终报价（`calculate-price`，`needTableware=false`，金额单位分）：

| 场景 | 请求要点 | `productPrice` | `price` | 与默认差额 | 字段 `diffPrice` | 一致？ |
|---|---|---|---|---|---|---|
| 默认套餐 | `9900005462`×1 | 3450 | **3450 分 = ¥34.50** | — | +¥0 | ✅ |
| 换大薯条（只传 round 2） | `roundList=[{round:"2",comboItemList:[{code:"4820"}]}]` | 3700 | **3700 分 = ¥37.00** | **+250 分** | +¥2.5 | ✅ |
| 换心形薯饼（只传 round 2） | `code:"521983"` | 3550 | **3550 分 = ¥35.50** | **+100 分** | +¥1 | ✅ |
| 换大薯条（全量传 3 个 round） | round1/2/3 都传 | 3700 | 3700 分 | +250 分 | +¥2.5 | ✅ |

结论：`roundList` 机制可用，**最终价差与 `diffPrice` 完全吻合**；只传目标 round 即可，不必全量回传。这不再是"字段差额冒充最终报价"。

**玉米杯换配**：`9900005462` 的 round 2 只提供 4 个选项，**不含** `4437`/`4438`。`9900005453`、`9900016073`、`9900004835`、`9900004236`、`9900011126`、`9900004066` 的 round 2 同样只有「中薯 / 心形薯饼 / 扭扭薯 / 大薯条」四项。→ **当前菜单下「中薯换小杯玉米杯」这个换配不存在**，无法报价。

**去酱的价格影响**：去料项 `price=0`，去酱后价格不变（¥22.50 → ¥22.50）是**合理结果**，不是价格接口故障。

|---|---|---|---|---|

## 二、对第一轮结论的修正

| 第一轮说法 | 修正 |
|---|---|
| 中薯→小杯玉米杯「减 68 kcal」 | **错**。官方单份差值为 **−236 kcal**。已作废 |
| 去酱后「417 kcal」 | 保留，但明确标注：来源为**二手转述的台湾数据**（`health.baidu.com` 用户发布内容），**未在台湾官网原页核实**，且**不是中国大陆同款酱料官方数据** |
| 去酱后「381 kcal 是上界」 | **取消"上界"表述**。381 kcal 来自"普通蛋黄酱标签 × 15 g 假设"，15 g **不是门店确认用量**。417 与 381 是两个**并列情景**，不能拼成可靠区间 |
| 「所有来源都没有钠」 | **错**。市售蛋黄酱标签（中国妇幼保健协会引用）每 100 g 含钠 **637 mg**，按 15 g 计算可估得 95.6 mg。因此问题不是"没来源"，而是"没有大陆麦香鸡酱的官方钠" |
| 去酱后钠「严格小于标准版」 | **取消**。情景A 无钠数据 → 去酱后钠为**未知**，不写"小于" |

修正后的两个情景（同一份标准版 2029 kJ / 485 kcal，P24 F24 C42 Na1208 Ca154）：

| 指标 | 情景A：台湾麦香鸡酱每份 | 情景B：普通蛋黄酱 15 g |
|---|---|---|
| 替代配料 | 台湾「麥香鷄醬」 | 市售蛋黄酱 |
| 份量假设 | 每份（未标克重） | **15 g（待用户确认）** |
| 能量 | 1744.5 kJ / 417 kcal | 1592.2 kJ / 380.6 kcal |
| 蛋白质 | 23.8 g | 23.6 g |
| 脂肪 | 17.5 g | 12.8 g |
| 碳水 | 39.7 g | 41.7 g |
| 钠 | **未知** | 1112.4 mg（弱依据） |
| 钙 | **未知** | **未知** |

代码里两个情景各自独立调用 `estimate_remove_sauce()`，**没有任何"取最小/最大"的拼合逻辑**。

## 五、实现要点

| 关注点 | 做法 |
|---|---|
| SKU↔营养绑定 | 只认两种证据：套餐 `rounds` 里 POS 自己标注的 code→名称；或名称完全相同（仅统一括号宽度）。不做删减式归一化 |
| 同名多规格 | 「玉米杯」不匹配「小杯玉米杯」/「大杯玉米杯」，判为数据缺失，不进规划，不按 0 |
| 同名重复条目 | 小杯玉米杯、纯牛奶（盒装）各 2 条，数值一致 → 报告为 `identical` 重复，不静默取一条 |
| 去酱估算 | 两个具名情景，各自带来源/替代配料/份量假设；缺项保持 `null` |
| 目标函数 | 五项归一化加权 + 0.08 主食重复惩罚，权重随结果返回 |
| 约束 | 只用用户输入；不设 90%/110% 隐性容忍 |
| 无解 | 列差额 + 最接近方案 + 明确"不视为达标" |
| 报价 | 每餐单独 `calculate-price`，带 `reservationDate`，金额分→元 |
| 摄入记录 | 锁定时保存营养/价格/来源快照；历史不因菜单更新而改写 |
| Token | 运行时从环境变量或本机配置读取，不入源码/前端/示例/fixture |

## 六、已知限制与未完成

1. **午餐/晚餐菜单无差异**，只能靠时点区分，无法做"晚餐专属"推荐。
2. **部分热门 SKU 无营养映射**（龙焰系列、可乐/玉米杯/派等未标规格条目），被排除在方案外。这是保守策略，不是 bug，但会降低可选性。
3. **加肉饼、少酱档位**在当前菜单不存在（`modification` 仅 0/1 二值），首版不做。
4. **去酱估算只覆盖"整份酱料"**，且两个情景的份量依据都不完整（A 无克重，B 的 15 g 未确认）。
5. **没有真实下单**，报价为试算参考价；未来结算价可能因促销变化。
6. 早餐池与正餐池按 SKU 集合自动区分，但接口不返回"这个 SKU 属于哪一餐"的显式字段，分类依赖名称关键词（`MAIN_WORDS`/`SIDE_WORDS`/`DRINK_WORDS`），存在误归类风险。
7. 单用户、单门店、到店自取；外送、多门店、账号体系未做。
