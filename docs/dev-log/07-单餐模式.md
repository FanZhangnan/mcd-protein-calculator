## 一、本版本采用严格模式

单餐模式只有一套营养口径，六条定义：

1. **所有营养数值只来自官方营养表的整款单份数据。**
2. **去除配料只作为「点单建议」**：会写进报价请求的 `modification`，让用户点到的就是这个版本；但营养数值保持标准版，不扣减任何数字。
3. **达标判断（热量、蛋白质、脂肪、碳水、价格）一律用标准版官方数值**，去除建议不参与判断。
4. 文案统一写：**「建议去掉 X。去掉后的营养官方未提供，此处显示标准版数值。」** 不说「更低」「小于」「约为」。
5. 如果去掉的配料可能含蛋白质（名称包含 **芝士、吉士、干酪、培根、蛋**），追加：**「去掉 X 后，蛋白质可能低于显示值。」**
6. **不新增组件估算数据**，不修改 `estimator.SCENARIOS`；单餐模式不使用去酱估算情景。三餐模式的估算功能保持原样。

「调整肉量」= 在官方整款汉堡之间升级（如 麦香鱼 → 双层深海鳕鱼堡），**不存在加肉饼**，API、UI、文案都不提供。

## 三、去除项能力查询

### `GET /api/removable?code=&meal=`

返回该 SKU 所有带 `unselectedKey` 的特调项，不再只看酱料：

```json
{
  "ok": true,
  "sku": {"code": "511782", "name": "芝士安格斯厚牛堡"},
  "meal": "lunch",
  "groups": [{"index": 0, "values": [
    {"code": "100201", "name": "醇香芝士风味酱", "selectedKey": "0-1", "unselectedKey": "0-0"},
    {"code": "102215", "name": "高达干酪片", "selectedKey": "0-1", "unselectedKey": "0-0"},
    {"code": "102225", "name": "番茄片", "selectedKey": "0-1", "unselectedKey": "0-0"},
    {"code": "120160", "name": "黄油", "selectedKey": "0-1", "unselectedKey": "0-0"}
  ]}],
  "options": [
    {"code": "102215", "name": "高达干酪片", "protein_risk": true, "default_suggestion": true, ...}
  ]
}
```

- 缓存键：`removable:{store}:{be}:{order}:{date}:{meal_time}:{code}`
- `protein_risk` 按严格模式第 5 条的关键词判断
- `default_suggestion` 覆盖 酱 / 芝士 / 吉士 / 干酪 / 培根 / 黄油
- 原有 `sauce_capability` 与 `/api/capability` 返回结构不变，只是内部改为按餐次时间查询

## 四、`suggest_remove` 定制

```json
{"action": "suggest_remove", "option_codes": ["102215"]}
```

- 每个 `option_code` 必须出现在 `removable_options()` 里，否则 400 `unsupported_customization`
- 按 `MCP_INTEGRATION.md §3.5`，**同一组的所有项一起传**：被去掉的用 `unselectedKey`，其余用 `selectedKey`
- `item.nutrition` 保持不变；`nutrition_basis = "standard_unadjusted"`；`is_estimate = false`
- `removal_notes` 写入严格模式第 4、5 条文案
- 取消后完整恢复；重复应用结果不变（从 baseline 重建，天然幂等）
- 签名包含 `modification`，改定制后旧试算价自动失效

真实结果（511782 去高达干酪片）：

```
营养     696 kcal / 32 g 蛋白 / 44 g 脂肪   ← 与标准版完全相同
basis    standard_unadjusted，is_estimate=false
modification 4 项：100201:0-1, 102215:0-0, 102225:0-1, 120160:0-1
报价     31.5 元 → 31.5 元（价差 0，去料 price=0）
```

## 五、单餐求解

### `POST /api/meal`

必填：`meal`、`protein_min`、`fat_max`、`budget`；可选：`carb_max`、`kcal_min`、`kcal_max`、`allow_side`。

内部复用三餐模式的 `Item` / `Targets` / `sum_nutrition` / `plan_open`：

```python
planner.plan_open(pools, targets, [meal],
                  ranker=planner.single_meal_rank,
                  full_enumeration=True)
```

结构与排序规则：

| 规则 | 实现 |
|---|---|
| 主食恰好 1 个、数量固定 1 | `build_meal_options` 每个组合只放一个 main，`quantity=1` |
| 饮品 0–1 杯，只从白名单 | 零度可乐 / 美式 / 纯牛奶 + 官方热量 < 20 kcal；含糖饮料排除 |
| 配菜 0–1 | `allow_side=false` 时 side 池为空 |
| 价格、脂肪硬约束 | `is_feasible()`；最接近方案也不放宽 |
| 排序 | 可行集优先 → 蛋白缺口最小 → 价格最低 → 脂肪最低（`single_meal_rank` 返回元组） |
| 候选范围 | `full_enumeration=True`，不做 beam 截断 |
| 达标判断 | 只用标准版官方数值 |

不读、不写 intake，不进入 replan。基线仍写入 `baseline.json`（`extra.mode="single"` + 单餐 targets），`/api/quote` 与 `/api/recompute` 沿用同一套签名和上下文校验。

### 无解时的可达上限

`planner.single_meal_frontier()` 枚举全部组合，返回：

- `max_protein`：在脂肪 ≤ F、价格 ≤ B 下蛋白质最高的组合
- `relax_fat`：只放宽脂肪，达到蛋白目标所需的最小脂肪
- `relax_price`：只放宽价格，达到蛋白目标所需的最低价格
- `reachable`：整份菜单是否存在任何蛋白 ≥ P 的组合；没有再报「达不到 P g」

### 用例 1：午餐 蛋白 ≥30、脂肪 ≤20、价格 ≤30

**无解**。硬约束下上限为 **23 g 蛋白质**（板烧鸡腿堡，17 g 脂肪，24 元）。只放宽脂肪或只放宽价格仍达不到。

### 用例 2：午餐 蛋白 ≥40、脂肪 ≤20、价格 ≤35

**无解**。整份菜单最高 **34 g**（培根安格斯厚牛堡，44 g 脂肪）；硬约束下上限 **23 g**。

```
只放宽脂肪，仍达不到蛋白质目标。
只放宽价格，仍达不到蛋白质目标。
```

## 九、剩余限制

- 单餐只判断「这一顿」；不累计到全天，也不读已吃记录
- 早餐可选蛋白上限受菜单限制：纯牛奶在菜单中但没有官方营养匹配，被排除，无法靠牛奶补蛋白
- `removable_options` 只返回 POS 提供 `unselectedKey` 的项；不同 SKU 的可去项不同
- 升级阶梯是人工维护的 5 对，只覆盖同系列；任一端不在售或无营养即隐藏
- 报价仍是时段试算参考价，不承诺结算价
- 单餐界面不提供数量修改（结构锁定为 1 份）；如需要多份，走三餐模式
- 未下单、未领券、未动积分、未建地址、未发布；用户真实 `data/` 已备份至 `data/backup-20261019-225139/`
