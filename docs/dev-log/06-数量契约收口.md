**项目**：麦麦健身餐管家
**日期**：2026-10-19
**范围**：只收口「待买数量」与「实际摄入数量」的契约，不改架构、不扩展功能。
**门店**：麦当劳珠海屏湾一路餐厅 `1440054`（到店自取）。

## 一、三个复现问题与根因

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 待买 0.5 份：营养按 0.5 算，`calculate-price` 却按 1 份收费 | `web/app.js` 的 `min=0.5 step=0.5`；`service.quote_meal()` 用 `int(max(1, round(q)))` 把 0.5 变成 1 | 前端 `min=1 step=1` + 本地校验；新增 `src/quantity.py`，`purchase_quantity()` 只接受正整数，`quote_meal()` 在任何 MCP 调用之前校验 |
| 2 | 514700 半份显示 209.5 kcal / 9.25 元，试算却是整份 18.50 元 | 同上：营养用小数，报价用取整后的整数，两个数字描述的不是同一份餐 | 契约统一：待买数量唯一来源是 `Item.quantity`，营养、行计、请求体都用它，且必须是整数 |
| 3 | `recompute` 接受 0，返回的签名随后被判 `stale_signature` | `recompute` 里 `max(0.0, qty)` 允许 0；`_items_from_dicts` 又用 `quantity or 1` 把 0 变回 1 | `recompute` 入口先校验全部待买数量；`_items_from_dicts` 不再 `or 1`，非法值直接拒绝；签名对 `2` / `2.0` 归一化 |

**关键原则**：不静默取整、不截断、不默认 1。非法输入必须是一个明确的 400，而不是一次"看起来成功"的报价。

## 二、规则

### 1. 待买数量（plan / recompute / quote）

| 输入 | 结果 |
|---|---|
| `1`、`2`、`3`、`"4"`、`5.0` | 接受，转成整数 |
| `0.5`、`1.5`、`2.5`、`0.1` | **400 `invalid_quantity`** |
| `0`、`-1`、`-0.5` | **400 `invalid_quantity`** |
| `""`、`"  "`、`null` | **400 `invalid_quantity`** |
| `"abc"`、`[]`、`{}` | **400 `invalid_quantity`** |
| `NaN`、`Infinity`、`-Infinity` | **400 `invalid_quantity`** |
| `true` / `false` | **400**（`bool` 是 `int` 子类，显式拒绝） |

拒绝时：

- 不改变最后一次有效的工作快照、基线或签名
- 不发起 `calculate-price`
- 前端恢复输入框为当前方案的有效数量，并在状态栏说明原因

### 2. 已吃数量（intake）

- 允许正的小数，例如 `0.5` 个汉堡；营养按 `每份 × 0.5` 计入
- **不重新报价**
- 记账金额独立保存：买整份花了 18.50，就记 18.50，不会因为只吃半份自动变成 9.25
- 参考价 `amount_reference` 仍按半份计算（单价 × 0.5），它只是参考，不是记账
- 已吃数量为 `0`、负数、空、非数字、`NaN`、`Inf` → 400，不写入记录

### 3. 报价一致性

- `quote_meal()` 逐项发送 `productCode / quantity / modification`
- 数量就是方案里的整数，商品和定制原样传递
- 报价返回后方案的商品、数量、定制不变
- 签名对 `2` 与 `2.0` 生成同一个哈希，避免"刚重算就失效"

## 五、剩余限制

- 待买数量只支持整份；**买整份吃半份**需要先在待买里买 1 份，再在已吃记录里填 0.5，没有"买 N 吃 M"的联动
- 已吃记录改数量时旧记账金额会作废（需重填），这是上一轮既定规则；本轮只是保证不会被自动除以 2
- 报价是时段试算参考价，不承诺结算价
- 午/晚餐菜单集合仍相同；加肉饼/少酱档位在接口层不存在；套餐换配仍未接入三餐求解
- 前端非法输入的恢复依赖 `PLAN` 当前值；如果页面在请求过程中被手动改乱，仍以服务端 400 为准
