# 16 · 券后价（门店真实试算）

> 目标：推荐方案旁边显示「券后要付多少钱」，金额必须来自麦当劳接口的带券试算，不能自己按折扣规则推算。
> 边界：只读查询 + 试算；不领券、不核销、不下单、不动积分、不建地址。

## 一、真实数据验证

券：**11.9 元麦辣鸡腿堡**（本人账号已在麦当劳 App 领取，券面有效期 2026-10-19 10:30 – 2026-10-23 23:59）。

| 项 | 值 |
| --- | --- |
| 门店 | 珠海屏湾一路 `1440054`，到店自取 |
| 取餐时点 | 2026-10-22 12:15 |
| 试算时间 | 2026-10-21 13:32:42（接口 `datetime`） |
| 商品 | 麦辣鸡腿汉堡 ×1（`1440`） |
| 不带券 | **23.00 元**（2300 分，`discount=0`） |
| 带券 | **11.90 元**（1190 分，`discount=1110`，`originalPrice=2300`） |

两次请求的唯一差别是 item 上多了 `couponId` / `couponCode`。**真实券 ID（不公开）**：仅运行时从接口取得，未写入仓库、fixture、日志或测试；本文与仓库中不留任何券 ID、券码或打码片段。

页面实测（`tests/coupon_ui.mjs`，7/7 通过）：

```
券后 11.90 元（用 11.9元麦辣鸡腿堡）· 原价 23.00 元 · 券后每元 2.0 g 蛋白质
券后价来自门店试算，下单时以 App 为准
```

## 二、接口

### `GET /api/coupons?meal=lunch`

只读转发 `query-store-coupons`，返回券名、适用商品名、有效期、是否需要先领取；**不含 couponId / couponCode**。

### `POST /api/quote_with_coupon`

```json
{"meal": "lunch", "signature": "当前方案的 signature"}
```

- 校验签名与门店上下文（过期返回 `409 stale_signature` / `409 stale_context`）。
- 先用 `quote_meal` 得到原价，再对每张「适用商品在方案里」的券调用 `calculate-price` 带券试算。
- **只保留金额真的低于原价的结果**，取最低的一张；否则 `status=none`。
- 返回 `coupon.amount`、`coupon.title`、`discount`、`protein_per_yuan`、`quoted_at`、`reservation_date`，并固定带 `note`：「券后价来自门店试算，下单时以 App 为准。」

券 id/code 只存在 `Service._coupon_raw` 内存中，按「门店 + 日期 + 餐次 + 餐次时间」为 key；不写缓存文件、不进 `/api` 返回、不打印。

## 三、页面

- 结果卡自动在方案出来后查询一次券；有降价才在价格区显示「券后价」，大数字改为券后金额，并显示原价删除线、券名、券后每元蛋白质。
- 没有券 / 没降价：一行「暂无可用券」，不显示任何推算金额。
- 换方案、改数量、去配料后签名变化，旧券后价清空并重查。
- 在线试玩页（快照）不显示券后价，因为没有登录账号；`snapshot-shim` 对券接口固定返回空。
- 排序不变：推荐方案仍按原价规则求解，券后价只做展示。

## 五、限制

- 券的可用性以门店 `query-store-coupons` 返回为准；未领取的券不在列表里，页面不会出现「可领」入口（本工具不领券）。
- 一次只应用一张券（取降价最多的一张）；多券叠加未验证，接口也未承诺支持。
- 券后价是所选时段的试算价，不是结算价；实际以 App 结算为准。
- 券会过期：换日期或券下架后重查会变成「暂无可用券」，属正常结果。
