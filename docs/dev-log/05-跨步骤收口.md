## 1. 三餐全吃后不得再次生成三餐

### 根因

```python
# 旧代码
open_meals = [m for m in (open_meals or MEALS)]   # [] 是 falsy -> 变成三餐
```

`plan_open` 的调用方在"全部已吃"时传 `[]`，却被当成"没指定 → 默认三餐"，于是又搜出 3 条未锁定餐次，全天从 1800 变成 2100。

### 修复

- `open_meals is None` → 三餐；显式 `[]` → **直接返回空方案**（`meals=[]`、`cost=0`），不构建可售池、不进入 beam 搜索
- `Service.plan()` 在 `open_list == []` 时连 `pools()` 都不调用，直接走 `merge_locked`
- `merge_locked` 改为**全天口径**判定：用 `evaluate_day(全部餐次, 全天目标)`

数学上：`全天合计 = 已吃 + 未吃`，`全天目标 − 已吃 = 剩余目标`，所以"未吃合计 vs 剩余目标"与"全天合计 vs 全天目标"等价。统一用后者表述，三餐全吃时依然成立。

### 回归（`tests/test_flows.py`）

| 用例 | 断言 |
|---|---|
| G1 | `plan_open(pools, targets, [])` 返回 `meals=[]`、`cost=0` |
| G2 | 三餐各 600 kcal 全部记录后：仍是 3 条、全部锁定、合计 1800；`Service.pools` 被 mock 成抛异常也不会触发 |
| G3 | 三餐各 700 kcal：全天 2100，`feasible=false`，热量差额 `+200` |
| G4 | 三餐各 400 kcal：全天 1200，热量差额 `-300` |
| G5 | 撤销晚餐后：只开放 `dinner`，另外两条保持锁定 |

## 2. 有已吃记录时，报价必须计算完整日预算

### 根因

- `Service.apply_quotes` 的 `effective = Σ 开放餐次报价`，把已吃的 60 元直接丢了
- `server._apply_quotes` 遍历 **所有** `result.meals` 写 `amount_actual = quote.amount`，锁定餐没有新报价 → 被写成 `None`

合成反例（预算 100，已吃 60，开放试算 50）旧输出：`cost=50, feasible=true`，早餐金额被清空。

### 修复：三本账分开

| 字段 | 含义 | 未知时 |
|---|---|---|
| `booked_total` | Σ 已吃记账金额（`amount_actual`） | `null` |
| `quote_total` | Σ 开放餐次成功试算 | `null` |
| `cost` | 全天合计 = booked + quote（无报价时 booked + 参考价） | `null` |

- `planner.evaluate_day()` 是**唯一**判定入口，规划 / 重算 / 重排 / 当前方案报价四条路径都调用 `Service.compose_payload()`
- 报价只写 `meal.quote`（含 `queried_at`、`reservation_date`、`amount`），**不再写 `amount_actual`**
- `amount_actual` 只属于已吃记录；`amount_source` 归一化为 `quoted`（采用试算价）/ `manual`（手填）/ `unknown`
- `budget_status`：`quoted` / `booked`（三餐全吃）/ `reference` / `not_evaluated` / `no_budget`
- 任一缺项 → `cost=null`、`not_evaluated`，并给出"完整日预算尚未评估（不按 0 元计算）"，营养重排不受影响

### 回归

| 用例 | 断言 |
|---|---|
| G6 | 已吃 60 + 试算 25+25 → `cost=110`，预算差额 `+10`，`feasible=false` |
| G7 | 已吃 `amount_actual=60`、`source=manual` 不被报价覆盖；开放餐 `amount_actual` 仍为 `null` |
| G8 | 已吃金额未知 → `not_evaluated`、`cost=null`，违规项带"记账金额"说明 |
| G9 | 开放餐试算失败 → `not_evaluated`、`cost=null` |
| G10 | 重排后未报价：按参考价，且参考价含已吃记账 |
| G11 | `apply_quotes(booked_total=...)` 与 `evaluate_day` 结论一致 |
| G23 | 只改记录数量不填金额 → 旧金额作废（`null`，来源 `unknown`） |
| G24 | 金额等于试算价且未显式指定来源 → 记 `quoted`；手填不同金额 → `manual` |

### 真实 HTTP 证据（实时 MCP）

```

全天参考价含已吃记账        · 128.0 vs 95 + 33.0

                            [{'constraint':'budget','value':128.0,'target':'≤100.00','gap':28.0}]
```

## 3. 设置变化后不得重新加载旧上下文基线

### 根因

`invalidate()` 只把 `_baseline` 置空；下一次 `get_baseline()` 发现内存为空，就去读 `baseline.json`，把上海旧方案原样加载回来，`recompute` 也没有任何上下文校验。

### 修复

- `set_baseline` 写入：

```json
{
  "version": 2,
  "context": {"cache_key": "...", "store_code": "1440054", "date": "2026-10-20",
               "be_type": 1, "order_type": 1, "meal_times": {...}},
  "plan_version": "<16 位签名>"
}
```

- `get_baseline()` 每次加载都与当前 `CacheContext` 逐字段比对；不匹配 → 返回 `None`（文件保留为证据，但**永远不会**再被当成可用基线）
- `recompute` 返回 `409 {"kind":"stale_baseline","error":"基线属于其他门店/日期/时段，已失效，请重新规划"}`
- `/api/bootstrap` 的 `baseline` 变成 `{exists, valid, reason, created_at, plan_version, context}`
- 前端保存设置 / 刷新菜单后调用 `clearPlanUI()`：清空 `PLAN / SIG / QUOTES / QTY / CUSTOM`，隐藏方案与汇总面板，并提示重新规划
- 历史摄入记录（`intake.json`）与原始菜单/营养证据**不受影响**

### 回归

| 用例 | 断言 |
|---|---|
| G12 | 同上下文基线可正常重算 |
| G13 | 切到 `1450713` + `invalidate()`：磁盘文件仍在，但 `get_baseline()` 返回 `None`，`recompute` → `stale_baseline` |
| G14 | 只改早餐时段同样失效 |
| G15 | 基线失效后历史记录仍在 |
| G18–G20 | 错误签名 / 缺失签名 / 上下文变化分别被 `quote` 拒绝 |

### 真实 HTTP 证据

```
旧基线被标记失效 · {"exists": true, "valid": false,
  "reason": "基线属于其他门店/日期/时段，已失效，请重新规划", ...}
旧基线重算被拒 409 · 409 stale_baseline
历史记录不随方案失效删除 · 1
```

## 4. 增加"当前方案重新报价"，保留用户修改

### 根因

`btn-quote` 调用的是 `/api/plan {quote:true}`，先重新求解、再报价；前端还顺手把 `QTY` / `CUSTOM` 清空。结果：早餐数量改成 2、全天 2270 kcal，点报价后回到 1 和 97.50 元。

### 修复

- `POST /api/quote {"signature": "..."}`
  - 只读 `Service._working`（最后一次 plan / recompute / replan 的方案快照）
  - **不调用** `plan_open` / `Service.plan`
  - 校验：无快照 `409 no_plan`；无签名 `400 missing_signature`；上下文变化 `409 stale_context`；签名不符 `409 stale_signature`
  - 只对未锁定餐次调 `calculate-price`，锁定餐沿用记账金额
- `recompute` / `replan` / `plan` 都会刷新 `_working` 与签名，因此"改数量 → 报价"用的是新签名
- 前端：`btn-plan` = 重新生成方案（会清空修改）；`btn-quote` = 为当前方案报价（保留修改）

### 回归

| 用例 | 断言 |
|---|---|
| G16 | 数量 2 + `modification` 原样进入 `calculate-price` 请求；返回方案数量仍为 2；`plan_open` / `Service.plan` 被 mock 成抛异常也不会触发 |
| G17 | 报价带 `queried_at`，且不再出现 `quoted_at` |
| G18 | 错误签名 → 409，且**没有**发起任何价格调用 |
| G19 | 空签名 → 400 |
| G20 | 换门店后 → 409 `stale_context` |
| G21 | `recompute` 后签名刷新，用它报价能带上新数量 |
| G22 | 报价失败 → `not_evaluated` / `cost=null` / `feasible=false`（不是 0 元的一天） |

### 真实浏览器证据（Chrome 155，实时 MCP）


## 5. 文案与字段统一

| 原 | 现 | 位置 |
|---|---|---|
| 计划餐"实付 X 元" | 未吃餐只显示「参考 X 元」；有试算时显示「试算价 X 元」 | 三餐卡片 |
| 已吃"金额：X 元（quoted）" | 「记账金额：X 元（采用试算价 / 手填 / 未知）」 | 已吃记录 |
| `q.quoted_at` | `q.queried_at`（后端只返回这一个字段） | 报价行 |
| "规划 + 逐餐真实报价" | 「重新生成方案」+「为当前方案报价」 | 按钮 |
| "总价（已按真实报价）" | 「全天合计（按试算价 / 按已吃记账 / 按参考价 / 尚未评估）」 | 汇总 |

浏览器阶段另外发现并修掉两个真实文案/交互缺陷：

1. **采用试算价记账被标成"未知"**：`record_meal` 在金额来自报价时没有写 `amount_source`（存成 `null`）。现按"金额 == 试算价 → `quoted`，否则 `manual`"归一化。
2. **默认情景下勾选去酱无提示**：`official_only`（仅官方数据）时，麦香鸡酱没有可直接扣除的官方标准版数据，后端会拒绝，但前端只是静默回滚。现在会明确提示"请先选择具名估算情景"，并且对"有酱料项但没有可引用成分数据"的 SKU 直接禁用勾选（不再让用户白点）。

## 9. 剩余限制

- **午餐与晚餐菜单集合相同**，只能靠时点区分。
- 部分新系列与未标规格 SKU（可乐/玉米杯/派）无营养映射，被排除在方案外。
- 加肉饼、少酱档位在接口层不存在；去酱估算只覆盖整份「麦香鸡酱」。
- 套餐换配仍是独立接口（`/api/swap`），未接入三餐求解，也不参与全天合计。
- 报价是**该时段试算参考价**，不承诺未来结算价；已吃金额只是本地记账，不是支付凭证。
- 报价签名绑定的是**方案内容**，不是服务器端的锁；同一签名在有效期内可重复试算。
- 工作快照 `_working` 只在内存中，服务重启后需要重新生成方案才能报价。
- 菜单名分类依赖关键词表，存在误归类风险。
- 单用户、单门店、到店自取；外送、账号体系、自动下单均未做。
